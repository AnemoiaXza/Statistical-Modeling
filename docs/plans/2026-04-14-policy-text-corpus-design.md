# 政策文本语料设计

## 文档目的

本设计文档用于固定“双碳”政策文本模块的语料范围、抓取策略、标注体系、聚合逻辑和验证要求。
该模块定位为主论文的`机制项 + 调节项`扩展，不改变主识别路线，不作为主处理变量。

## 一、模块定位

### 1. 研究角色

政策文本模块只承担以下作用：

- 解释为何不同城市中数字普惠金融的减排效应存在差异
- 刻画政策环境是否强化数字普惠金融的绿色作用
- 为异质性与机制分析提供可解释的制度背景变量

该模块不承担以下作用：

- 不作为主处理变量
- 不作为主识别设计
- 不做简单“情绪评分”

### 2. 与主线模型的关系

主线保持为：

- `D`：数字普惠金融指数
- `Y`：碳排放强度为主、碳排放总量为稳健性
- `X/W`：城市层面控制变量

政策文本指标进入模型的方式限定为：

- 机制变量
- 调节变量
- 异质性解释变量

## 二、语料范围

### 1. 时间窗

- `2020-01-01` 至 `2024-12-31`

### 2. 层级

语料覆盖三层：

- 中央
- 省级
- 地级市

### 3. 城市归属规则

政策文件向 `city-year` 面板分配时采用行政隶属归属：

- 中央文件分配给所有样本城市
- 省级文件分配给该省全部样本城市
- 地级市文件只分配给本市

### 4. 纳入口径

先采用窄口径纳入标准。

标题或正文需明确涉及以下主题之一：

- `双碳`
- `碳达峰`
- `碳中和`
- `节能降碳`
- `绿色低碳`
- `数字绿色融合`
- `数字化绿色转型`

### 5. 暂不纳入的文本

第一阶段默认剔除以下文本：

- 与绿色低碳无明确关联的纯产业扶持文件
- 与绿色低碳无明确关联的纯数字经济文件
- 新闻稿
- 政策解读稿
- 领导讲话摘要
- 转载稿

## 三、抓取设计

### 1. 第一阶段源站

第一阶段仅覆盖以下源站：

- `gov.cn`
- `ndrc.gov.cn`
- `mee.gov.cn`
- 省级人民政府官网
- 最终样本城市对应的地级市政府官网

### 2. 抓取原则

抓取策略采用`站点适配器`模式，不做万能爬虫。

原因：

- 官方站点结构差异大
- 正文可能为 HTML、PDF 或扫描件
- 元数据字段并不统一
- 需要长期可维护和可复现

### 3. 抓取流程

抓取流程拆成四层：

#### A. 发现层

在目标站点按关键词 + 年份发现候选文件。

发现规则：

- 优先使用站内列表页、专题页、搜索结果页
- 记录发现入口 URL
- 保留标题、发布日期、候选链接

#### B. 正文层

进入正式发布页面，获取：

- HTML 正文
- 附件 PDF
- 原始链接

#### C. 规范化层

统一抽取以下字段：

- `doc_id`
- `title`
- `pub_date`
- `issuing_body`
- `doc_no`
- `admin_level`
- `region_name`
- `region_code`
- `source_url`
- `source_site`
- `content_text`
- `attachment_path`
- `raw_html_path`
- `is_pdf`
- `is_scanned_pdf`

#### D. 去重层

去重优先级如下：

1. 同文号去重
2. 无文号时按 `标题 + 日期 + 发文机关` 去重
3. 正式发布页优先于转载页

### 4. PDF 处理策略

第一阶段不追求一次性解决全部 PDF 问题。

- 可直接抽文本的 PDF：正常解析
- 扫描件 PDF：标记为 `ocr_pending`
- OCR 不作为第一阶段硬前置条件

### 5. 第一阶段产物

第一阶段必须生成以下产物：

- `政策主表`：一行一份政策文件
- `原文仓`：保存 HTML 与 PDF 原件
- `抓取日志`：记录失败页、扫描件、去重结果、异常情况

## 四、标注设计

### 1. 总体策略

采用`规则抽取 + LLM 评分`的混合方案。

不采用纯 LLM 打分的原因：

- 可复核性较弱
- 评审追问时不够稳
- 不利于后续做一致性校验

不采用纯规则指数的原因：

- 过于粗糙
- 难以体现政策文本内容差异
- 创新性不足

### 2. 规则变量

文档级规则变量包括：

- `has_quant_target`
- `has_deadline`
- `has_responsibility`
- `has_assessment`
- `has_digital_term`
- `policy_level`

这些变量主要服务于：

- 规则解释
- 模型辅助验证
- 与 LLM 分数的对齐校验

### 3. LLM 核心指标

文档级只保留 3 个核心分数：

- `policy_strength`
- `execution_clarity`
- `digital_green_synergy`

含义如下：

- `policy_strength`：政策约束力度、任务密度、推进强度
- `execution_clarity`：责任分工、时间节点、考核执行安排是否清晰
- `digital_green_synergy`：是否明确体现数字化手段服务绿色低碳转型

## 五、聚合设计

### 1. 聚合单位

最终聚合到：

- `city-year`

### 2. 聚合口径

每个核心分数同时保留两套聚合方式：

- 年度加总
- 年度均值

建议字段示例：

- `sum_policy_strength_city_year`
- `mean_policy_strength_city_year`
- `sum_execution_clarity_city_year`
- `mean_execution_clarity_city_year`
- `sum_digital_green_synergy_city_year`
- `mean_digital_green_synergy_city_year`

### 3. 聚合解释

- `sum` 更接近政策压力总量
- `mean` 更接近当年政策平均质量

两套口径同时保留，后续可根据模型表现决定主机制口径与稳健性口径。

### 4. 层级权重

第一版不人为设置中央、省、市的数值权重。

原因：

- 权重主观性强
- 难以在论文中充分论证
- 先保留层级字段，后续如有必要再做分层聚合或扩展权重方案

## 六、验证设计

政策文本指标必须经过验证后才能进入正式实证。

最低验证要求包括四项：

### 1. 人工复核样本

抽取一批政策文本进行人工标注，与模型输出对照。

### 2. 重复提问一致性

对同一文本重复评分，检验 LLM 输出是否稳定。

### 3. 规则-LLM 对齐

检验规则变量与 LLM 分数是否方向一致，例如：

- 有量化目标的文件，其 `policy_strength` 应整体更高
- 有责任部门和考核条款的文件，其 `execution_clarity` 应整体更高

### 4. 极端样本检查

检查最高分和最低分文本是否符合研究直觉，避免明显误判。

## 七、实施边界

本模块的执行边界如下：

- 不改变主因果识别路线
- 不替代主结果变量
- 不改变主控制变量体系
- 不将探索性文本结果直接提升为 headline result

若后续出现以下事项，需重新确认：

- 语料口径从窄口径扩展到泛政策口径
- 中央、省、市权重方案进入主结果
- LLM 指标从机制/调节上升为主解释变量
- 新增超出当前三指标的核心文本评分体系

## 八、建议的下一阶段实现顺序

1. 确定第一阶段站点清单与样本城市清单
2. 建立政策文件原始数据目录结构与元数据主表
3. 实现官方页面抓取与附件下载
4. 实现正文规范化与去重
5. 实现规则变量抽取
6. 设计 LLM 标注提示词与输出 schema
7. 进行小样本人工复核与一致性校验
8. 聚合到 `city-year`，并与主面板预留接口

## 九、交付标准

当以下条件同时满足时，政策文本模块可进入建模联调阶段：

- 已形成可追溯的政策文件主表
- 原始文本可回溯到官方源站或官方附件
- 规则变量抽取稳定
- LLM 三指标完成小样本验证
- `city-year` 聚合表可与主面板按城市和年份匹配

## 十、实现落地约定（2026-04-14）

当前仓库内的落地约定如下：

- CLI 入口固定为 `src/08_policy_text.py`
- 政策文本临时产物写入 `data/interim/policy_text/`
- 聚合后产物写入 `data/processed/policy_text/`
- 阶段性说明与运行摘要写入 `logs/policy_text/`
- 环境依赖至少包括 `requests`、`beautifulsoup4` 与 `pypdf`

实现时仍需遵守以下边界：

- 脚手架与目录创建可以先行，但文本指标仍仅服务于机制/调节分析
- 评分与聚合阶段必须保留可复核日志，避免形成不可追溯的黑箱指标
- 当主线识别与政策文本模块发生冲突时，以主线识别设计稳定性优先
